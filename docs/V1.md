# Synapse 1.0.0 — Collective Intelligence

This release consolidates the 0.19 runtime. Version 1.0.0 is a release milestone, not a certification of production readiness. Use a single OpenCode writer per project. All existing schema-1 run, idea, experiment and ledger records remain readable; no schema migration or new npm dependency.

## Operational checks

- `npm run doctor -- --project /absolute/project/path` inspects inventories, cooperative locks and ledger coverage, without new model requests. Exit 0 means its checks passed; exit 1 means attention/unavailable. It does not certify provider health, dependencies, permissions or actual plugin activation. The offline CLI may initialize an empty directory while listing records; it does not repair records.
- `synapse_doctor` is the coordinator-only runtime counterpart; includes local resource reservations. A live lock is not necessarily a fault. The check is a snapshot, not a transaction.
- `npm run health -- --project /absolute/project/path` queries OpenCode for the active server plugin and expected source; `synapse_version` confirms the actual loaded version.
- `npm run typecheck`, `npm audit` and `npm test` validate dependencies/types/tests locally after installation.

## Cooperative local locks

On local filesystems supporting atomic mkdir, rename and hard links, a graph update holds `<data>/.locks/run_ID.update` during its read-modify-write transaction; `run_ID.execute` is held for admission and graph execution. A competing engine cannot execute or stop the same graph. Updates wait up to 10 seconds on disk contention (the in-instance queue can wait longer); execution admission fails immediately. Proposal updates, deliberation and configuration edits have equivalent locks under `<data>/evolution/.locks`. New proposal snapshots use atomic exclusive publication. Locks are cooperative: older releases, manual edits and tools not respecting these locks can bypass them. No shared worker slot limit across engines, no global experiment isolation, no transaction over logs, scans, registration, multiple records or remote sessions. No distributed or multi-host use. Atomic publication is not a power-loss durability guarantee.

An abrupt process exit can leave a lock directory behind. Do **not** delete one during normal use. To recover: close OpenCode interfaces, finish/interrupt outstanding work, stop the service, verify that no other local writer or remote session may still be active, back up the entire project data directory, and use the doctor to identify the precise lock. Only once the owner is known to be gone, manually remove the specific empty directory with `rmdir -- /exact/path/to/.locks/run_ID.execute` (or the corresponding update/deliberate lock). Never recursively purge the locks directory or delete graph data. An old execution can have consumed attempts or left remote side effects; inspect the run before explicitly resuming it. There is no automatic lock stealing.

## Economics

`functionalEligible` indicates a completed graph. `economicEligible` and the existing `performanceEligible` field now also require clean retained input accounting and minimum worker/reviewer coverage inferred from recorded attempts and completed reviewed tasks. This lower bound does not establish complete history or billing. Other token categories retain their own coverage indicators. Comparisons remain advisory; zero reported dollars is not proof of free use. No automatic model switch, weakened review, or spending policy change.

## Installation and restoration

Use the versioned Bash installer as an unprivileged user; finish active missions and close all clients first. It retains the stable install path, copies recognized local configuration, backs up the global configuration and prior installation, and captures a private copy of the initialized target project's XDG directory before replacement. Other project directories are left untouched. Back up those separately if needed. It refuses outstanding target locks after service stop. The installer prints backup and staging directories; keep them private. It does not automatically restore XDG on failure, because this might overwrite newly written data.

Manual rollback: stop all clients and the service; inspect the backup and current directory; move the current installation aside (do not delete it), restore `previous-install` at the exact old stable path, and restore only the corresponding backed-up OpenCode configuration files after reviewing changes. Keep current XDG data; restore the private XDG snapshot only after making a separate copy of current data and verifying that all writers are stopped. Restart and verify the plugin with `npm run health` and `synapse_version`. Never run two different releases against the same store at once. Do not share the private backup archive as a diagnostic.

## Release gates

Local tests verify contention, independent Node processes, crash-residual locks, economic coverage and coordinator-only doctor. No model calls are made by the local suite. Still required for a production qualification: full SDK typecheck, fresh npm audit, successful controlled Lean comparison (provider quota permitting), real complex reviewed code mission, and multi-agent circuit behavior on the real host. A subsequent real-host diagnostic confirmed activation and retained records. The dependency registry was unavailable during packaging; do not infer a clean audit.
